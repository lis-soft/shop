# 需求文档：非卡单刷单商品金额区间（可配置）

> 状态：需求分析（已复审修订）  
> 客户表述：中台可配置；用户端不用改  
> 工程落地：后端必改；中台需有配置入口（见 §2.2）  

---

## 0. 复审结论（先看这段）

上一版文档有三处容易误导，已在本文纠正：

| 问题 | 说明 |
|------|------|
| 「只改后端、中台可不改」说得太满 | 客户要的是**中台能自行控制**比例。只改后端、配置埋在库里，运营在中台页面改不到，**不等于交付客户原话**。 |
| 「设置页加 defaultConfigs 就能自动出现」不可靠 | 中台设置页对多数配置是**按 key/分组特制 UI**；新 key 丢进 `website` 或许能挤进通用列表，但不等于有合格的「刷单规则」入口。要对齐客户，应明确：**后端选品 + 中台可改两项百分比**。 |
| 把旧逻辑简化成「换个百分比」偏乐观 | `task_force===0` 还有整轮佣金目标 950~1050 的选品策略；`task_force>0` 还有 VIP1 随机/贴近余额等策略。换成余额百分比后，这些策略是**删除、保留为区间内二次筛选、还是另议**，文档必须单列，不能假装只改两个数字。 |

**仍然成立、且重要的判断：**

- 用户端 `user`：**不用改 UI**（刷单页不选商品，只展示后端派的单）。
- 真正决定「看到多少钱的商品」的代码在：**`constructdigital-backend` → `OrderService.createOrder`**。
- 卡单（`UserTask.continuous_order`）应继续优先，不受该百分比约束。

---

## 1. 需求原话（客户）

> 不卡单时调整商品金额范围……刷单商品的范围可以自行控制……  
> 非卡单：余额 1000，中台设置 30-80%，展示 300-800 的商品。

客户口头「只改中台」应读作：

- **配置权在中台**（运营改 30/80）
- **用户端不要动**
- **不是**「代码仓库里只提交 `admin`、完全不动后端」

---

## 2. 要改哪些项目（对齐客户 + 可交付）

### 2.1 必改

| 项目 | 改什么 | 为什么 |
|------|--------|--------|
| `constructdigital-backend` | 非卡单自动选品按「可用余额 × min%~max%」 | 不改这里，设了百分比也不生效 |
| `constructdigital-backend` | 新增两个全局配置项（默认如 30/80） | 百分比要可配置，不能写死 |

### 2.2 为满足「中台自行控制」——中台也要有入口

| 项目 | 改什么 | 为什么 |
|------|--------|--------|
| `admin` | 设置页增加两项：最低%/最高%（或独立「刷单规则」区块） | 否则运营无法在中台「自行控制」，只能改库/调接口 |

若客户书面确认「先由技术改库配置、中台页面以后再做」，可把 `admin` 标为二期；**否则默认一期包含中台入口**。

### 2.3 不改

| 项目 | 原因 |
|------|------|
| `user` | 无商品列表筛选；展示的是已派订单 |
| 卡单派单弹窗 `AssignOrderModal` | 卡单逻辑，本需求不覆盖 |

## 3. 需求理解（白话）

| 概念 | 含义 |
|------|------|
| 刷单 | 用户端流程页点任务，后端 `POST /api/order/create` **自动派一个商品单** |
| 卡单 | 中台给用户配的手动派单（`continuous_order`），可指定商品/价，可超余额 |
| 非卡单 | 本轮序号未命中卡单时，走自动选品 |

**目标公式（客户示例）：**

```text
商品价格 ∈ [余额 × 30%, 余额 × 80%]
例：余额 1000 → [300, 800]
```

「刷单页面展示」= 用户看到的那张已派订单上的商品金额，不是前端再滤一遍货架。

## 4. 现状（代码事实）

入口：`user` Process → `createOrder`  
文件：`constructdigital-backend/src/api/services/OrderService.js`

### 4.1 决策顺序

1. 校验用户 / 禁止抢单 / 可用余额 / 未完成单 / VIP / 本轮单量  
2. **有卡单且序号命中** → 手动派单（可超余额）  
3. **否则自动选品**（下方硬编码）

### 4.2 非卡单硬编码（与需求冲突）

| 分支 | 行为 |
|------|------|
| `task_force === 0` | `_selectNormalProduct`：`price ≤ min(余额, 3400)`，并按本轮总佣金目标约 **950~1050** 挑品；无货则 `findAffordableProduct`（任意 ≤ 余额） |
| `task_force > 0` 且 VIP1 | `min = max(余额×0.35, 3500)`，`max = 余额×0.45`；区间内再随机/排序 |
| `task_force > 0` 其它 | `min = 3500`，`max = 可用余额`；无货同样回退任意 ≤ 余额 |

配置表 / `defaultConfigs.js`：**没有**「刷单金额占余额 %」项。

因此：余额 1000、想看 300~800 的商品，在现有第二轮及 VIP1 逻辑下经常对不上（3500 下限等）。

---

## 5. 目标行为（验收）

1. 中台可配置全局 `min_percent` / `max_percent`（示例默认 30 / 80）。  
2. **仅非卡单**自动派单使用。  
3. 计算基数建议：`availableBalance = balance - frozen_balance`（**待确认**：客户说的「余额」是否含冻结）。  
4. `minPrice = availableBalance * min% / 100`，`maxPrice = availableBalance * max% / 100`。  
5. 只选 `status=1` 且 `price ∈ [minPrice, maxPrice]` 的商品。  
6. 卡单 / 幸运单：不变。  
7. 区间无货：策略见 §6，**默认建议直接失败**，禁止再回退到区间外「任意 ≤ 余额」。

### 示例

| 可用余额 | 配置 | 期望派单价格 |
|----------|------|----------------|
| 1000 | 30–80 | 300–800 |
| 800（余额1000冻结200） | 30–80 | 240–640（若采用可用余额） |

---

## 6. 必须拍板的问题（未确认前不宜开发扫尾）

1. **「余额」**：总余额还是可用余额（总 − 冻结）？  
2. **无匹配商品**：报错 / 贴边选 / 旧回退（旧回退与需求冲突，不推荐）？  
3. **旧策略如何处置**（关键）：  
   - 整轮佣金目标 950~1050是否废除？  
   - VIP1 的 35%~45% + 3500 是否废除？  
   - `task_force>0` 的 3500 下限是否废除？  
   - 区间内二次挑选（随机 / 贴近余额 / 按佣金）保留哪一种？  
4. **作用域**：全局一套，还是按 VIP / 轮次多套？（原话像全局）  
5. **`task_force===0` 是否与后续轮次同一套百分比？**（建议同一套）  
6. **一期是否必须上中台设置 UI？**（对齐「自行控制」则建议必须）

## 7. 修改内容（修订后）

### 7.1 后端 `constructdigital-backend`（核心）

**A. `src/config/defaultConfigs.js`**

新增例如：

- `auto_order_price_min_percent` = `30`  
- `auto_order_price_max_percent` = `80`  

建议独立 `group`（如 `order` / `task`），**不要塞进「网站文案」分组糊弄**；description 写清「非卡单刷单商品金额占可用余额比例」。

**B. `src/api/services/OrderService.js`**

- `createOrder` 非卡单分支：用配置计算 `[minPrice, maxPrice]` 选品，替换 3500 / 0.35 / 0.45 等。  
- `_selectNormalProduct`：与上统一，或删除佣金目标策略（取决于 §6 拍板）。  
- 自动派单路径停止滥用 `findAffordableProduct` 越界回退。  
- 卡单 / 幸运单分支：**不动**。

### 7.2 中台 `admin`（对齐客户「自行控制」）

**`src/views/settings/index.vue`（及必要时 `defaultConfigs` 的 group 展示）**

- 增加可编辑的最低% / 最高%  
- 保存前校验 `0 < min ≤ max ≤ 100`  
- 文案标明：仅影响非卡单自动刷单  

> 仅加后端 `DEFAULT_CONFIGS`、指望网站通用列表「碰巧显示」——**不作为正式方案**。

### 7.3 用户端 `user`

不改。

## 8. 自测用例

1. 可用余额 1000，30–80，无卡单 → 价格 ∈ [300,800]  
2. 同用户存在卡单且序号命中 → 仍出卡单价，可超余额  
3. 改配置为 10–50 后再派 → 新区间生效（中台改完即可测）  
4. 区间内无上架商品 → 按拍板策略失败或贴边，**不出区间外单**  
5. 非法 min>max → 保存拒绝或读取回退默认  

---

## 9. 一句话

客户要的是：**中台能配置非卡单刷单金额占余额的比例，用户按该比例看到对应价位商品**。  
实现上：**后端改选品逻辑（必做）+ 中台加配置入口（要对齐客户原话就必做）+ 用户端不改**。  
上一版把「中台可不改」写得过轻，且低估了替换现有佣金/3500 等旧策略的产品决策量——以本文为准。
